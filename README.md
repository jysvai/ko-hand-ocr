(`tools/vs.py` — 누구를 어떻게 돌렸는지는 [아래](#다른-ocr-과-같은-자로-견주면)). 그 아래는
우리 두 모델의 항목별 성적이고, `tools/verify.py` 로 글씨체마다 810~963줄씩 잰 값이다.
**단일 모델**은 41M 모델 하나로 읽는다. **앙상블**은 모델 3개가 같이 읽고 서로 닮은 답을
고른다 — 더 정확하고 일곱 배 느리다. 초록 줄은 사진을 통째로 읽는 우리
[VL 모델](https://huggingface.co/localdeel/ko-hand-ocr-vl)(0.8B)이다 — LM Studio·Ollama 에
그대로 올라간다([아래](#lm-studio--ollama--vllm-과-같이-쓰기)).

> **2026-10-08 에 시험지를 고쳤다.** 동해독도·기랑해랑 시험지에 그 글꼴이 못 그리는 글자
> (빈칸·□)가 든 줄이 섞여 있어서 다 맞혀도 97.5% 였다. 그 줄을 빼고 모두 다시 쟀다(나머지 네 벌은
> 그림까지 같다). 그래서 이 README 의 글씨체 숫자는 **그 전 숫자보다 높게 나온다** — 모델이
> 바뀐 것이 아니다. 사진 숫자는 그대로다.

## 되는 것 — 그리고 안 되는 것

**된다**

- **사진 한 장을 통째로.** 줄을 찾아 자르고 각각 읽는다 (`read_photo`)
- **이미 잘린 줄 그림**을 묶음으로 (`read`)
- **가둬서 읽기** — 후보 목록 안에서만 고르게 하고, 자유롭게 읽은 것과 맞는지 알려 준다 (`both`)
- **앙상블로 읽기** — 모델을 여럿 두고 서로 닮은 답을 고른다
- **아무 데도 보내지 않는다.** CPU 에서 완전히 혼자 돈다
- **LM Studio·Ollama·vLLM 쪽 도구와 붙는다** — 같은 말을 하는 서버와 MCP 도구(아래 「LM Studio · Ollama · vLLM 과 같이 쓰기」)

**안 된다**

- 표 안의 칸을 라벨과 값으로 갈라 주지 않는다. `read_photo` 는 줄까지만 자른다
- 세로쓰기, 칸 병합은 다루지 않는다
- 읽을 것이 없는 칸(전체가 낙서인 것)도 무언가 읽어 낸다

## 왜 만들었나

우리가 찾아본 가운데 한국어 **손글씨**를 노리고 공개된 모델은 `ddobokki/ko-trocr` 하나였는데,
학습 자료가 AI Hub 라 이용 목적·재배포에 제약이 붙는다. 사내 도구에 넣거나 공개 꾸러미로
배포하려면 걸린다. 두루 쓰는 OCR(PaddleOCR·EasyOCR·Tesseract)과 큰 VLM 은 손글씨 한
줄에서 크게 떨어진다 — 같은 시험지에서 그 가운데 가장 잘 읽는 것이 글씨체 6벌
78.2%, 사진 78.5% 다(아래). 그래서 **이 일을 하는 모델을
처음부터 다시 만들었다** — 부품마다 출처를 따져 볼 수 있게.

## 다른 OCR 과 같은 자로 견주면

상대는 여섯이다. 한국어 OCR 로 사람들이 실제로 꺼내 쓰는 것을 갈래마다 세웠다.

| 상대 | 갈래 | 크기 | 어떻게 돌렸나 |
|---|---|---|---|
| `ddobokki/ko-trocr` | 한국어 TrOCR (AI Hub 로 배움) | 214M | transformers, float32, 빔 5, 길이 상한 16 -> 64 로 풀어 줌 |
| PaddleOCR PP-OCRv5 | 줄 인식기 (`korean_PP-OCRv5_mobile_rec`) | 3.3M | paddleocr 3.7.0 / paddle 3.4.0, `TextRecognition` |
| EasyOCR | 줄 인식기 (`korean_g2`) | 4.0M | easyocr 1.7.2, `Reader(["ko", "en"]).recognize()` |
| Tesseract 5 | 줄 인식기 (LSTM, 파라미터 수는 공개하지 않는다) | 파일 6MB | tesseract 5.5.3, `--oem 1 --psm 7 -l kor+eng` |
| PaddleOCR-VL-1.6 | OCR 전용 VLM | 906M | transformers 5.16.1, bfloat16, 물음 「OCR:」(모델 카드) |
| Qwen3-VL-2B-Instruct | 두루 쓰는 VLM | 2.1B | transformers 5.16.1, bfloat16, 한글 물음 — 셋을 대 보고 가장 잘 읽은 것 |

모두 **모델 카드의 사용법 그대로**다. 엔진마다 따로 깐 환경에서 돌리고
(`tools/rival_worker.py`), 시간은 그 엔진이 잰 값만 센다(그림을 넘기는 값은 뺀다).

견줌이 성립하려면 **모델만 다르고 나머지는 같아야** 한다. 사진은 우리 줄
자르기(`kohandocr.page`)로 자른 **같은 칸**을 모두에게 넣었고, 글씨체 시험지는
`synth.render` 가 그린 **날것**을 넣었다 — 우리 전처리(64×640 letterbox)를
씌워서 주면 상대만 두 번 찌그러진다. 자·GPU·잰 순간이 모두 같다. 무엇을 어떻게
쟀는지는 `tools/vs.py` 머리말에 다 적혀 있고, 아래 숫자는 전부 그것이 남긴
`runs/VS.json` 에서 나왔다.

- **상대 여섯 가운데 가장 잘 읽는 것도 큰 차이로 뒤진다.** 안 배운 글씨체 6벌에서
  상대 으뜸은 ko-trocr 78.24%, 우리 단일 모델(41M)은 96.80% 다. 두루 24벌에서도
  ko-trocr 80.45% 대 97.26%.
- **사진 열한 장은 아무도 본 적이 없다.** 거기가 가장 깨끗한 자리이고, 우리 앙상블
  96.52% · 단일 모델 94.24% 대 상대 으뜸 ko-trocr 78.50% 다. 줄을 통째로 맞힌 비율은
  67.6% 대 26.5%(상대 가운데 가장 높은 값).
- **큰 VLM 이라고 손글씨 한 줄을 잘 읽지는 않는다.** Qwen3-VL-2B(2.1B)는 6벌
  66.56%, PaddleOCR-VL-1.6(906M)은 63.71% 다. 우리보다 스무 배에서 쉰 배 크지만 이
  일에 맞춰 배운 모델이 아니다. 문서 전체를 읽는 일이라면 이야기가 다르다(재지 않았다).
- **Tesseract 는 손글씨를 거의 못 읽는다**(6벌 17.73%, 사진 13.21%). 인쇄 글자용
  엔진이라 예상한 대로다. 기준선으로 둔다.
- **글꼴을 하나도 안 빼고 480벌을 읽혀도** 우리 98.29%(앙상블) · 98.11%(단일 모델) 대
  상대 으뜸 ko-trocr 82.58%. **우리가 본 적 없는 24벌(99.00%)이 학습에 쓴
  450벌(98.24%)보다 높다** — 외워서 올라간 숫자가 아니라는 뜻이다. PaddleOCR-VL 은 가장
  싼 묶음이 줄당 1초 안팎이라 480벌은 재지 않았다(표에서 빈칸).
- **그래도 무너지는 벌이 있다.** 480벌 가운데 우리 단일 모델의 가장 낮은 벌이
  47.31%, 앙상블은 63.21% 다. 여섯 벌만 보면 이런 벌이 안 보인다.
  벌당 12줄뿐이라 한 벌의 값은 크게 흔들리므로 무리 합계와 분포로 본다.
- **단일 모델은 사진 바닥이 0.3.0 보다 낮다.** 가장 나쁜 장이 hand-06
  83.03% 다 — 세 줄짜리 장의 한 줄(`전자금융TF서약`)이다.
  앙상블에서는 다른 모델이 받아 주어 90.28% 그대로다.
- **사진 통째를 읽는 VL 모델도 같이 쟀다**(초록). [ko-hand-ocr-vl](https://huggingface.co/localdeel/ko-hand-ocr-vl)
  (0.8B)은 줄을 하나씩 읽혀도 글씨체 6벌 97.01% 로 단일 모델(96.80%)과 비슷하고 가장
  낮은 벌은 더 높다(94.96 대 93.14%). 사진 줄 칸은 93.42% 로 조금 낮고, 스무 배 크고
  CPU 에서 일곱 배 느리다. 그 모델의 쓰임은 **줄을 자르지 않고 사진 통째를 읽는 것**과
  **LM Studio·Ollama 에 그대로 올라가는 것**이다. 사진 통째로는 그쪽 설명서에 상대 VL
  들과 견준 값이 있다(쪽 단위 94.3% 대 72.7~79.9%).

### 같지 않은 것 — 어느 쪽에 유리한지까지 적는다

| 무엇이 | 어떻게 | 누구에게 유리 |
|---|---|---|
| 시험 글꼴 | 여섯·스물네 벌은 **우리** 학습에서만 뺐다. 상대가 무엇을 보고 배웠는지 우리는 모른다 | 상대 |
| 줄 자르기 | 상대에게 우리 것을 빌려주었다(모두 한 줄 그림을 받는다) | 상대 |
| 길이 상한 | ko-trocr 의 기본은 `max_length: 16`(글자 단위). VLM 둘과 같이 64 토큰으로 풀어 주었다. Qwen3-VL 이 상한에 닿은 줄은 모두 되풀이로 넘친 줄(`11 11 11 …`)이었고 긴 정답이 잘린 줄은 없었다(2026-10-07 에 글씨체 670줄을 다시 읽혀 보니 상한에 닿은 24줄이 모두 그랬다) | ko-trocr |
| 물음 | Qwen3-VL 은 정해 둔 OCR 물음이 없어 셋을 대 보고 가장 잘 읽는 것을 주었다 | Qwen3-VL |
| 정밀도 | VLM 셋(우리 VL 포함)은 나온 정밀도(bfloat16) 그대로, 나머지는 float32. ko-trocr 는 float16 빠르기도 따로 쟀다 | — |
| VLM 의 CPU | 줄당 몇 초에서 수십 초라 1줄 묶음을 한 번만 쟀다. 8줄로 묶으면 더 빠를 수도 있다 | ko-hand-ocr |
| 480벌 | PaddleOCR-VL 은 줄당 1초 안팎이라 480벌 전부는 안 쟀다(빈칸) | — |
| 만든 목적 | 줄 인식기 셋은 주로 인쇄·장면 글자, VLM 둘은 문서 전체, ko-trocr 는 AI Hub 의 손글씨·공공행정문서. **손글씨 한 줄 하나만 노리고 만든 것은 우리 쪽이다** | ko-hand-ocr |
| 모델 수 | 우리 앙상블은 모델 셋(36M 하나 + 41M 둘, 118M). 크기로 견주려면 「단일 모델」 줄을 본다 | ko-hand-ocr |
| 학습에 쓴 글꼴 | 480벌 가운데 450벌은 **우리가 본 글씨체**다. 그래서 무리를 갈라 적는다 | ko-hand-ocr |
| 그리개 | 우리는 시험지와 **같은 그리개**(`synth.render`)로 그린 합성 그림으로 배웠다(글꼴은 다르다). 글씨체 시험지의 생김새가 우리에게 낯익다 — 그래서 사진 쪽이 가장 깨끗한 견줌이다 | ko-hand-ocr |

**상대들이 나쁜 모델이라는 뜻이 아니다.** 인쇄 서류·장면 글자·문서 전체를 읽으라고
만든 모델에 손글씨 한 줄을 들이민 것이고, 그 일에서는 이쪽이 낫다는 것뿐이다. 반대
방향(인쇄 서류 전체, 표, 장면 글자)은 재지 않았고, 재면 우리가 질 가능성이 크다.

잰 자리: NVIDIA GeForce RTX 5060 Laptop GPU · AMD Ryzen 7 260 · torch 2.14.0+cu130 ·
2026-10-09 07:25. 2026-10-08 에 시험지를 고친 뒤 열 모델을 한 번에 다시 잰 것이다(VL
설명서에만 싣는 Qwen3.5-0.8B 원본은 이 표에서 뺐다). 사진 쪽은 그 전 판(2026-10-07)과
글자 하나까지 같다 — 사진은 고친 것이 없다. 빠르기는 그때그때 기계 상태를 타므로
**같은 순간에 잰 것끼리만** 견준다.

## 빨리 써 보기

```python
from kohandocr.reader import Reader

reader = Reader("ko-hand-ocr-single", device="cpu")   # 푼 폴더

# 사진 한 장을 통째로. 줄 자르기까지 해 준다.
reader.read_photo(open("scan.jpg", "rb").read())
# -> ['보안점검표', '부서 : 포테토뭉부서', '이름 : 감자밭']

# 이미 줄을 잘라 두었다면 그림을 바로 넘긴다. 묶음으로 넣어야 빠르다.
reader.read([cell_a, cell_b, cell_c])

# 후보 목록이 있으면 그 안에서만 고르게 가둘 수 있다.
reader.both([cell_b], options=["포테토뭉부서", "감자밭", "김클로드"])
# -> [{'text': '부서 : 포테토뭄부서', 'constrained': '포테토뭉부서', 'agrees': True}]
```

**가둔 결과만 믿으면 안 된다.** 가둬 놓았으니 모델은 반드시 목록 안의 값을
내놓는다. 목록에 없는 것이면 엉뚱한 답이 나오고, 그것만 보면 틀린 줄 모른다.
`agrees` 가 거짓이면 사람에게 넘겨야 한다.

### 앙상블로 읽기

모델마다 잘 읽는 칸이 엇갈린다. 같은 자료로 조금 더 학습했을 뿐인데 어떤 칸은
살고 어떤 칸은 죽는다 — 그 칸을 아슬아슬하게 읽고 있다는 뜻이다. 그래서 모델을
여럿 두고 **여러 번 같게 나온 답**을 고른다.

```
받은폴더/
  config.json  vocab.json  model.safetensors
  also/
    v20b/  config.json  vocab.json  model.safetensors
    v19/   ...
```

`also/` 가 있으면 `Reader` 가 알아서 쓴다. 부르는 법은 그대로다.

확신도로 합치는 것은 재 봤고 **안 됐다** — 틀린 답을 더 확신하는 일이 있어서다.
그래서 확신도가 아니라 **서로 얼마나 닮았나**로 고른다.

## LM Studio · Ollama · vLLM 과 같이 쓰기

**모델을 그대로 올리고 싶으면 [ko-hand-ocr-vl](https://huggingface.co/localdeel/ko-hand-ocr-vl)
을 쓴다.** Qwen3.5-0.8B 를 구조 그대로 한글 손글씨로 미세조정한 VL 모델이라 새 코드 없이
올라가고, 사진을 자르지 않고 통째로 읽는다. 설정(욕심 뽑기, 생각 끔)까지 같이 들어 있어서
받자마자 쓴다.

```bash
ollama run hf.co/localdeel/ko-hand-ocr-vl-GGUF:Q8_0      # Ollama
lms get https://huggingface.co/localdeel/ko-hand-ocr-vl-GGUF@q8_0   # LM Studio
```

대신 스무 배 크고(1.6GB) CPU 에서 일곱 배 느리다. 잘라 둔 줄을 빨리 많이 읽을 것이면 이
41M 이 낫다.

**이 41M 모델은 그대로는 못 올린다.** 셋은 글을 이어 쓰는 LLM 을 돌리는 엔진이다. LM Studio·Ollama 는
llama.cpp 의 GGUF 만, vLLM 은 자기가 아는 구조만 돌린다. 이 모델은 그림 인코더에 교차 주의
디코더를 단 TrOCR 꼴이고 자모 어휘와 줄 자르기가 따로 있어서, GGUF 로 바꿀 수도 그 목록에
넣을 수도 없다. 대신 **그 엔진들과 같은 말(API)을 하는 서버**와 **MCP 도구**를 넣었다.

```bash
pip install "ko-hand-ocr[mcp]"      # 서버만 쓸 거면 [mcp] 는 빼도 된다
```

### 서버 — OpenAI·Ollama 와 같은 말

```bash
ko-hand-ocr-serve                   # 허깅페이스에서 단일 모델(156MB)을 받아 127.0.0.1:8765 에 띄운다
ko-hand-ocr-serve --ensemble        # 앙상블(450MB)
```

| 부르는 쪽 | 이렇게 |
|---|---|
| `openai` 클라이언트, vLLM 을 부르던 코드 | `base_url="http://127.0.0.1:8765/v1"` 로 바꾼다. 그림은 `image_url` 에 base64 로 |
| `ollama` CLI | `OLLAMA_HOST=127.0.0.1:8765` 를 주고 `ollama run ko-hand-ocr "C:\scan.jpg"` · `ollama list` |
| curl | `curl --data-binary @scan.jpg http://127.0.0.1:8765/read` |

```python
import base64
from openai import OpenAI

client = OpenAI(base_url="http://127.0.0.1:8765/v1", api_key="none")
picture = "data:image/jpeg;base64," + base64.b64encode(open("scan.jpg", "rb").read()).decode()
reply = client.chat.completions.create(model="ko-hand-ocr", messages=[
    {"role": "user", "content": [{"type": "image_url", "image_url": {"url": picture}}]}])
print(reply.choices[0].message.content)     # 줄마다 한 줄
```

- **글로 물은 것은 쓰지 않는다.** 그림을 줄로 잘라 읽고 줄마다 한 줄씩 돌려줄 뿐이다. 요약·정리는
  못 한다 — 그건 채팅 모델 몫이다(아래 MCP).
- **그림 주소(`http://…`)는 받으러 가지 않는다.** base64 로 실어 보낸다. 아무 데도 나가지 않는다.
- 기본은 이 PC(`127.0.0.1`)에서만 열린다. 비밀번호가 없으니 `--host 0.0.0.0` 은 믿는 망에서만.

### LM Studio — MCP 도구로

LM Studio(0.3.17 부터)의 채팅 모델은 바깥 도구를 부를 수 있다(MCP). `~/.lmstudio/mcp.json` 에:

```json
{"mcpServers": {"ko-hand-ocr": {"command": "ko-hand-ocr-mcp"}}}
```

`ko-hand-ocr-mcp` 가 PATH 에 없으면 전체 경로를 적는다(가상환경의 `Scripts\ko-hand-ocr-mcp.exe`).
그 뒤 도구를 부를 줄 아는 채팅 모델에게 "C:\scan.jpg 읽고 표로 정리해 줘" 라고 하면, 모델이
`read_handwriting` 으로 글자를 받아 정리한다. **글자를 알아보는 것은 이 모델, 정리는 채팅
모델**이다. 채팅 창에 붙인 그림은 도구에게 오지 않으므로 파일 경로로 준다. 처음 부를 때 모델을
받는다(156MB, 이 PC 에서 20~30초). 그다음은 사진 한 장에 1초 안팎이다.

**확인한 것과 안 한 것.** `ollama` CLI 0.34(`list`·`show`·`run`), 공식 `openai` 클라이언트(한
번에·흘려 받기), MCP SDK 2.3 손님으로 불러 보았다. LM Studio 채팅 창과 Open WebUI 화면 안에서
끝까지 해 본 것은 아직 아니다.

vLLM 자체에 넣으려면 플러그인으로 모델 구조를 새로 써야 한다. 41M 모델이라 GPU 서버로 얻을 것이
작아서 하지 않았다 — 위 서버가 vLLM 과 같은 OpenAI 주소를 낸다. vLLM 에 모델로 올릴 것이면 위
VL 모델이 Qwen3.5 구조 그대로다(우리는 Windows 라 vLLM 위에서는 직접 돌려 보지 않았다).

## 얼마나 맞히나

두 가지로 잰다. **둘 다 봐야 한다.** 아래는 전부
`python tools/verify.py` 로 낸 값이다(글씨체 벌마다 810~963줄, 사진 11장).

| | 안 배운 글씨체 (평균) | 가장 낮은 글씨체 | 손글씨 사진 11장 | 가장 나쁜 장 | 95% 넘긴 항목 |
|---|---|---|---|---|---|
| 단일 모델 (0.4.1) | 96.6% | 92.7% | 94.9% | 84.2% | 12 / 17 |
| 앙상블 (모델 3개) | 96.6% | **93.1%** | **96.6%** | **90.3%** | **13 / 17** |
| *0.4.0 단일 모델 (v83)* | *96.4%* | *92.6%* | *95.0%* | *83.0%* | *11 / 17* |

글씨체는 벌마다 1,000줄을 뽑고, 그 글꼴이 못 그리는 글자가 든 줄을 뺀다 — 963줄,
동해독도 814줄, 기랑해랑 810줄이다. 기울임 줄은 지난 릴리스이고 같은 자로 다시 쟀다
(2026-10-09). **2026-10-08 에 시험지를 고쳐서 그 전에 낸 글씨체 숫자와는 견주지
않는다** — 고친 것은 맨 위에 적었다. 0.3.0 은 새 시험지로 다시 재지 않아서 표에서 뺐다
(그 전 시험지로 잰 견줌은 아래에 있다).

**0.4.1 에서 바뀐 것은 단일 모델 하나다.** 앙상블(모델 3개)이 다음 글자마다 내는
확률을 단일 모델이 따라 배우게 하고(증류), 그렇게 배운 모델을 0.4.0 의 v83 과
반씩 섞었다. 크기·구조가 그대로라 빠르기도 같다. 17개 가운데 95% 를 넘긴 것이
11 -> 12개(hand-07 94.4 -> 95.8%), 글씨체 여섯 벌이 모두 조금씩 올랐고(가장 낮은 벌
92.6 -> 92.7%), 가장 나쁜 장 hand-06 이 83.0 -> 84.2% 다. 대신 hand-08 이 100 ->
96.7% 로 내려갔다. **크게 나아진 것은 아니다** — 사진 평균은 95.0 대 94.9% 로 같다.
같은 방법을 세기만 바꿔 다시 해 보거나(몫 0.25·1.0), 드롭아웃·무게 지수 평균·SAM
으로 해 본 것은 모두 v83 을 못 넘었다.

**0.4.0 은 0.3.0 에서 무엇이 나아졌나**(그 전 시험지로 잰 값). 단일 모델(v83)은 글씨체
평균 94.6 -> 95.5%, 가장 낮은 벌 88.5 -> 90.1% 로 올랐다. 대신 **사진 바닥이 내려갔다**
(hand-06 90.3 -> 83.0%, 세 줄짜리 장의 한 줄). 앙상블은 바닥을 그대로 지키고 사진 평균이
95.8 -> 96.6% 로 올랐다. 17개 항목(글씨체 6 + 사진 11) 가운데 95% 를 넘긴 것이 앙상블
10 -> 12개다.

자모 단위 닮음이고, 사진 쪽은 사진 한 장에 한 표다.

**사진 숫자를 그대로 기대하면 안 된다.** 만든 사람의 사진 11장 35칸으로 잰
값이라 폭이 ±5%p 다. 남의 손씨에 더 가까운 값은 **'안 배운 글씨체' 쪽**이다 —
학습에 한 번도 안 쓴 글꼴 여섯 벌로만 시험한 것이라 폭이 절반이다(±2~3%p).

**앙상블의 값은 평균이 아니라 바닥에 있다.** 글씨체 평균은 이제 같은데
(96.6 대 96.6) 가장 낮은 글씨체가 92.7% 에서 93.1% 로 올라가고, 단일 모델이
84.2% 로 흘린 장(hand-06)이 90.3% 가 된다. 한 모델이 아슬아슬하게 읽는 칸을 다른
모델이 받아 주기 때문이다.

**대신 모든 장이 좋아지지는 않는다.** 단일 모델이 95.2% 로 넘긴 장이 92.9% 로
내려가기도 한다(hand-10) — 두 모델이 같이 틀리면 맞게 읽은 한 모델이 밀린다.
그리고 일곱 배 느리다. 한 장이라도 사람 손으로 넘어가면 곤란한 자리에는
앙상블을, 많은 양을 빨리 훑어야 하면 단일 모델을 쓴다.

### 시험지가 실제로 어떻게 생겼나

![안 배운 글씨체 시험지](https://raw.githubusercontent.com/jysvai/ko-hand-ocr/main/holdout-sample.png)

글씨체마다 세 줄씩, 정답과 모델이 읽은 것과 닮음을 같이 적었다. 오른쪽의 옅은
띠는 64×640 틀에 맞추느라 남은 자리다 — 모델이 실제로 보는 그림 그대로다.

**여기 있는 짧은 서식 줄은 여섯 벌이 다 맞힌다.** 2026-09-02 에 같은 그림을
뽑았을 때는 동해독도의 '안전사무국' 이 틀렸는데 지금은 맞는다. 글씨체 사이가
벌어지는 자리는 이런 줄이 아니라 **긴 문장과 언어 지식이 안 통하는 줄**이다 —
시험지의 3분의 1은 뜻이 없는 음절을 이어 붙인 줄이라(획만 보고 읽는 힘을
기르려고 일부러 넣는다) 글자 하나만 어긋나도 되돌릴 여지가 없다.

생김새로 보면 **싱글데이**는 글자가 서로 떨어져 있고 획이 온전해서 인쇄체에
가깝고, **동해독도**와 **기랑해랑**은 획이 뭉개지고 생략된다. 아래 표의 차이가
그 차이다.

이 그림은 **글꼴 파일이 아니라 그림**이다. 글꼴로 글자를 그리는 것은 OFL 이
허용한다. 재배포하지 않는 것은 `.ttf` 파일 쪽이다
([PROVENANCE.md](https://github.com/jysvai/ko-hand-ocr/blob/main/PROVENANCE.md)).

## 속도와 사양 (실측)

GPU 가 필요 없다. 자모를 하나씩 차례로 뽑는 것이 병목이라 코어를 늘려도
별로 안 빨라지고, 반대로 **약한 PC 에서도 느려지지 않는다.**

CPU 로만, 사진 11장(칸 35개)을 재서 가운데값을 쓴다. 시간을 **자르기와 읽기로
나눠** 적는다 — 모델 수를 줄여도 자르기는 안 줄고, 사진 한 장에 서너 줄뿐이면
자르기가 절반을 넘는다.

| | 자르기 | 읽기 | 사진 한 장(3.2줄) | 줄당 | 30줄 서류 한 쪽 |
|---|---|---|---|---|---|
| 단일 모델, 빔 5 | 0.48초 | 0.57초 | 1.04초 | 0.18초 | 6.9초 |
| 단일 모델, 그리디 | 0.48초 | 0.30초 | 0.78초 | 0.09초 | 2.0초 |
| 앙상블, 빔 5 | 0.48초 | 4.36초 | 4.83초 | 1.37초 | 47.1초 |

2026-10-07 에 쟀다. 같은 날 0.4.0 의 단일 모델(v83)은 사진 한 장 1.00초·줄당 0.17초
였다 — 크기와 구조가 같아서 **0.4.1 이 더 무겁거나 느리지 않다**(5% 안쪽은 재는
날의 흔들림이다). **날마다 기계 상태가 달라서** 2026-09-22 에는 같은 v83 이 줄당
0.25초로 나왔다. 그래서 같은 날 잰 값끼리만 견준다.

메모리는 사진 11장을 읽는 동안의 최댓값으로 단일 모델 약 1.07GB, 앙상블 약 1.51GB
다. 2026-09-22 에 쟀다(0.4.1 단일 모델은 구조가 같다).

**8층은 공짜가 아니다.** 2026-09-22 에 같은 자로 0.3.0 의 6층 모델(v62)을 다시 재면
줄당 0.18초(빔 5)·0.09초(그리디), 메모리 1.03GB 였고, 그날 8층 모델은 0.25초였다.
빔 5 에서 **40% 쯤 느리다.** 빠르기가 먼저면 v0.3.0 의 v62 를 받는다.

**오른쪽 칸을 그냥 곱해서 얻은 것이 아니다.** 우리 시험 사진은 한 장에 서너
줄인데 남들이 말하는 「한 쪽」은 서른 줄짜리 서류다. 잰 쪽당 초를 그대로
들이대면 우리 쪽이 열 배쯤 유리한 숫자가 나온다. 그래서 묶음을 키워 가며
**줄당 초가 얼마나 내려가는지**를 재고 그 값으로 환산한다
(`python tools/bench.py --throughput`).

`python tools/bench.py --all --device cpu` 로 낸 값이다. 그 자는 앱이 지나는
길을 그대로 지난다 — 다른 길로 잰 속도는 쓰는 사람의 속도가 아니다.

## 학습

데이터를 굽지 않는다. 글월을 만들고 손글씨 글꼴로 그려서 **그때그때** 먹인다.
그래서 디스크에 학습 데이터가 남지 않고, 분포를 바꾸면 다음 걸음부터 바로 반영된다.

```bash
python tools/fetch_fonts.py                       # OFL 손글씨 글꼴을 받는다
python -m kohandocr.train --out runs/v1 --layers 8 \
       --steps 20000 --batch 40 --workers 5 --letters 128 \
       --strike 0.15 --warp 0.5 --digits 0.04
```

뒤의 셋은 **학습 자료만** 바꾼다. 시험지는 늘 기본값으로 그리므로 켜고 꺼도
자는 그대로다(끄면 난수도 안 뽑는다 — 시험이 지킨다).

- `--strike` — 지운 자국을 넣을 줄 비율. 사진 37칸 가운데 넷에 지운 자국이 있다.
- `--warp` — 글자 **속** 획을 휠 줄 비율(`synth._warp`). 그 전까지의 흔들기는
  글자를 통째로만 움직여서 자모 모양은 글꼴 그대로였는데, 사진에서 틀리는
  자리가 전부 자모 하나였다(금->글, 감->갈, 피->회).
- `--digits` — 날짜가 **아닌** 숫자 줄로 바꿀 비율(`corpus.digit_line`). 학습
  글월에 날짜 든 줄이 맨 숫자열보다 두 배 많아서, 숫자가 흐리면 모델이 날짜
  틀로 지어냈다(`'816883539' -> '2025-05-19'`).

글꼴 자리는 이 차례로 찾는다. **경로를 코드에 박지 않는다.**

1. `--fonts` 로 준 값
2. 환경 변수 `KOHAND_FONTS`
3. `~/.cache/ko-hand-ocr/fonts`

`--layers` 를 안 주면 4층으로 만든다. 내놓는 단일 모델은 8층이다(앙상블에는 6층
하나가 섞여 있다). 4층은 조리법을 열세 바퀴 바꿔도 글씨체 평균 92.8~93.4% 에서
안 움직였고 6층이 그 띠를 처음 넘었다. 6층도 열세 바퀴 동안 가장 낮은 항목이
90.1% 에 붙어 있었는데, 8층에 글자 속 획 휘기를 더한 모델부터 앙상블 구성이
다시 바뀌었다. 층을 늘려서 치르는 CPU 속도는 6층에서 8층으로 40% 쯤이다(같은 자로
잰 값) — 인코더와 입력 크기는 건드리지 않았다.

`fetch_fonts.py` 가 받는 것은 손글씨 글꼴 482벌이다. 그 가운데 **452벌로만
학습하고**, 여섯 벌은 위의 시험에, 스물네 벌은 「두루 읽나」에 쓴다. 시험용과
같은 디자인이 학습에 섞이면 숫자가 조용히 오르므로, 이름이 아니라 **그림으로**
견주어 닮음 0.7 이상이면 비켜 놓는다.

글꼴은 이 저장소에 들어 있지 않고 **재배포하지 않는다.** 나눔손글씨 109벌은
[clova.ai/handwriting](https://clova.ai/handwriting) 에서 받는다. 자세한 것은
[PROVENANCE.md](https://github.com/jysvai/ko-hand-ocr/blob/main/PROVENANCE.md).

합성이 실제 손글씨와 얼마나 닮았는지는 `kohandocr/measured.json` 에 적힌
실측 분포(잉크량, 밀도, 가로세로, 여백 등 아홉 가지)로 견준다.

```bash
python tools/match.py        # 과녁과 지금 합성을 나란히 본다
```

**오래 돌린다고 좋아지지 않는다.** 합성 분포를 바꾼 뒤에는 짧게 돌고 중간 저장을
남겨서 골라야 한다(실측: 15,000걸음이 꼭짓점이고 30,000걸음은 오히려 내려갔다).

```bash
python tools/pick.py runs/v1-15000 runs/v1-30000    # 남긴 저장들을 재서 고른다
```
