## 한눈에

| | |
|---|---|
| **읽는 것** | 사진 속 손글씨 한 줄 (한글 + 영문) |
| **모델** | ViT-Small 인코더(ImageNet, Apache-2.0) + 6층 TrOCR 디코더(처음부터 학습) |
| **어휘** | 자모 229개 — 음절 11,172자를 외우지 않는다. 못 본 글자도 쓴다 |
| **파라미터** | **36M** — `ko-trocr`(213.7M)의 1/6 |
| **판(가중치)** | **138MB** 하나 · 414MB 셋 *(따로 받는다)* |
| **꾸러미** | 83KB — 코드만 |
| **속도** | **줄당 0.17초** · 사진 한 장 0.99초 — **GPU 없이 CPU 만으로** |
| **메모리** | 905MB 하나 · 1.18GB 셋 |
| **성적** | 학습에 안 쓴 글씨체 여섯 벌 평균 **94.6%** (판 셋이면 95.3%) · 가장 낮은 벌 88.5% (판 셋 90.3%) |
| **학습 자료** | 합성 — OFL 글꼴로 그때그때 그린다. 디스크에 남지 않는다 |
| **라이선스** | Apache-2.0, 가중치도 같다 — **자료에서 물려받는 약관이 없다** |
| **필요한 것** | Python 3.10+ · PyTorch 2.5+ |

## 되는 것 — 그리고 안 되는 것

**된다**

- **사진 한 장을 통째로.** 줄을 찾아 자르고 각각 읽는다 (`read_photo`)
- **이미 잘린 줄 그림**을 묶음으로 (`read`)
- **가둬서 읽기** — 후보 목록 안에서만 고르게 하고, 자유롭게 읽은 것과 맞는지 알려 준다 (`both`)
- **여러 판으로 읽기** — 판을 여럿 두고 서로 닮은 답을 고른다
- **아무 데도 보내지 않는다.** CPU 에서 완전히 혼자 돈다

**안 된다**

- 표 안의 칸을 라벨과 값으로 갈라 주지 않는다. `read_photo` 는 줄까지만 자른다
- 세로쓰기, 칸 병합은 다루지 않는다
- 읽을 것이 없는 칸(전체가 낙서인 것)도 무언가 읽어 낸다

## 왜 만들었나

한국어 손글씨 OCR 로 공개된 것은 사실상 `ddobokki/ko-trocr` 하나뿐인데, 학습 자료가
AI Hub 라 이용 목적·재배포에 제약이 붙는다. 사내 도구에 넣거나 공개 꾸러미로
배포하려면 걸린다. 그래서 **같은 일을 하는 모델을 처음부터 다시 만들었다** —
부품마다 출처를 따져 볼 수 있게.

![ko-hand-ocr 와 ko-trocr 비교](https://raw.githubusercontent.com/jysvai/ko-hand-ocr/main/bench-compare.svg)

## ko-trocr 와 같은 자로 견주면

위 그림은 **약관과 덩치**를 견준 것이다. 읽는 실력은 따로 쟀다.

견줌이 성립하려면 **모델만 다르고 나머지는 같아야** 한다. 사진은 우리 줄
자르기(`kohandocr.page`)로 자른 **같은 칸**을 둘 다에 넣었고, 글씨체 시험지는
`synth.render` 가 그린 **날것**을 넣었다 — 우리 전처리(64×640 letterbox)를
씌워서 주면 그쪽만 두 번 찌그러진다. 자·정밀도(float32)·빔 너비(5)·GPU·잰
순간이 모두 같다. 무엇을 어떻게 쟀는지는 `tools/vs.py` 머리말에 다 적혀 있고,
아래 숫자는 전부 그것이 남긴 `runs/VS.json` 에서 나왔다.

- **GPU 에서도 앞선다**(9.4 대 6.0줄/초, 1.6배). 우리는 판 셋을 흔들기 셋으로
  읽어 **한 칸에 판독을 아홉 번** 돌고도 그렇다. 판 하나로 가면 51.1줄/초로

- **묶음 크기는 짐작하지 않고 잰다.** 우리는 16줄, ko-trocr 는 8줄 묶음이 가장
  쌌다 — 그쪽은 384×384 인코더라 묶을수록 오히려 비싸진다. 이 카드에 안
  들어가는 묶음은 재지 않는다 — ko-trocr 의 32줄 묶음이 그렇고, 자가 적어 놓은
  까닭은 「앞 묶음 4642MB 의 두 배가 카드 8151MB 를 넘는다」이다. **안 잰 값을
  잰 것처럼 적지 않는다.**

### 같지 않은 것 — 어느 쪽에 유리한지까지 적는다

| 무엇이 | 어떻게 | 누구에게 유리 |
|---|---|---|
| 시험 글꼴 | 여섯·스물네 벌은 **우리** 학습에서만 뺐다. ko-trocr 가 AI Hub 에서 무엇을 봤는지 우리는 모른다 | ko-trocr |
| 길이 상한 | ko-trocr 의 기본은 `max_length: 16`(글자 단위 토크나이저). 64 로 풀어 주었다 | ko-trocr |
| 줄 자르기 | ko-trocr 에는 없다. 우리 것을 빌려주었다 | ko-trocr |
| 만든 목적 | ko-trocr 는 AI Hub 「다양한 형태의 한글 문자 OCR」·「공공행정문서 OCR」로 배웠다. **손글씨 한 줄만 노린 모델이 아니다** | — |
| 판 수 | 우리 앙상블은 36M 판 셋(108M). 크기로 견주려면 「판 하나」 줄을 본다 | ko-hand-ocr |
| 학습에 쓴 글꼴 | 480벌 가운데 450벌은 **우리가 본 글씨체**다. 그래서 무리를 갈라 적는다 | ko-hand-ocr |

**ko-trocr 가 나쁜 모델이라는 뜻이 아니다.** 인쇄된 공공행정문서를 읽으라고
만든 모델에 손글씨 한 줄을 들이민 것이고, 그 일에서는 이쪽이 낫다는 것뿐이다.
반대 방향(인쇄 서류 전체)은 재지 않았고, 재면 우리가 질 가능성이 크다.

## 빨리 써 보기

```python
from kohandocr.reader import Reader

reader = Reader("ko-hand-ocr-v62", device="cpu")   # 푼 폴더

# 사진 한 장을 통째로. 줄 자르기까지 해 준다.
reader.read_photo(open("scan.jpg", "rb").read())
# -> ['보안점검표', '부서 : 포테토뭉부서', '이름 : 감자밭']

# 이미 줄을 잘라 두었다면 그림을 바로 넘긴다. 묶음으로 넣어야 빠르다.
reader.read([cell_a, cell_b, cell_c])

# 후보 목록이 있으면 그 안에서만 고르게 가둘 수 있다.
reader.both([cell_b], options=["포테토뭉부서", "감자밭", "김클로드"])
# -> [{'text': '부서 : 포테토뭄부서', 'constrained': '포테토뭉부서', 'agrees': True}]
```

**가둔 결과만 믿으면 안 된다.** 가둬 놓았으니 모델은 반드시 목록 안의 값을
내놓는다. 목록에 없는 것이면 엉뚱한 답이 나오고, 그것만 보면 틀린 줄 모른다.
`agrees` 가 거짓이면 사람에게 넘겨야 한다.

### 여러 판으로 읽기

판마다 잘 읽는 칸이 엇갈린다. 같은 자료로 조금 더 학습했을 뿐인데 어떤 칸은
살고 어떤 칸은 죽는다 — 그 칸을 아슬아슬하게 읽고 있다는 뜻이다. 그래서 판을
여럿 두고 **여러 번 같게 나온 답**을 고른다.

```
받은폴더/
  config.json  vocab.json  model.safetensors
  also/
    v20b/  config.json  vocab.json  model.safetensors
    v19/   ...
```

`also/` 가 있으면 `Reader` 가 알아서 쓴다. 부르는 법은 그대로다.

확신도로 합치는 것은 재 봤고 **안 됐다** — 틀린 답을 더 확신하는 일이 있어서다.
그래서 확신도가 아니라 **서로 얼마나 닮았나**로 고른다.

## 어떻게 생겼나

```
  64 x 640 줄 그림
          |
   ViT-Small 인코더           facebook/deit-small-patch16-224 (ImageNet-1k, Apache-2.0)
   패치 16                    이미 배운 가중치를 낮은 배움 속도로 이어서 학습
          |
   TrOCR 디코더               6층, 머리 6개 — 백지에서 시작
          |
   자모 229개                 ㄱ ㅏ ㅁ ... 을 모아 '감'
          |
      "부서 : 감자밭"
```

결과의 대부분은 두 가지 판단에서 나왔다.

**음절이 아니라 자모.** 음절 11,172자를 통째로 외우려면 출력층이 커지는데도
드문 글자는 여전히 틀린다. 자모 229개를 모으면 어떤 음절이든 만들 수 있어서,
학습에서 한 번도 못 본 글자도 쓸 수 있다 — **이름을 지켜 준다.**

**인코더를 얼리지도, 세게 흔들지도 않는다.** 인코더는 ImageNet 에서 이미 눈을
떴다. 그래서 낮은 배움 속도로 이어 가고, 백지인 디코더는 빨리 배우게 둔다.
둘을 같은 속도로 흔들면 인코더가 알던 것이 망가진다.

## 얼마나 맞히나

두 가지로 잰다. **둘 다 봐야 한다.** 아래는 전부
`python tools/verify.py` 로 낸 값이다(글씨체 벌마다 400줄, 사진 11장).

| | 안 배운 글씨체 (평균) | 가장 낮은 글씨체 | 손글씨 사진 11장 | 가장 나쁜 장 |
|---|---|---|---|---|
| 판 하나 (v62) | 94.6% | 88.5% | 95.4% | 90.3% |
| 판 셋 | **95.3%** | **90.3%** | **95.8%** | **90.3%** |

자모 단위 닮음이고, 사진 쪽은 사진 한 장에 한 표다.

**사진 숫자를 그대로 기대하면 안 된다.** 만든 사람의 사진 11장 35칸으로 잰
값이라 폭이 ±5%p 다. 남의 손씨에 더 가까운 값은 **'안 배운 글씨체' 쪽**이다 —
학습에 한 번도 안 쓴 글꼴 여섯 벌로만 시험한 것이라 폭이 절반이다(±2~3%p).

**판을 여럿 두는 값은 평균이 아니라 바닥에 있다.** 평균은 조금만 앞서는데
(95.3 대 94.6) 가장 낮은 글씨체가 88.5% 에서 90.3% 로 올라가고, 판 하나가
93.3% 로 흘린 장(hand-08)이 100% 가 된다. 한 판이 아슬아슬하게 읽는 칸을 다른
판이 받아 주기 때문이다.

**대신 모든 장이 좋아지지는 않는다.** 판 하나가 100% 로 맞힌 장이 96.7% 로
내려가기도 한다(hand-05) — 두 판이 같이 틀리면 맞게 읽은 한 판이 밀린다.
그리고 여덟 배 느리다. 한 장이라도 사람 손으로 넘어가면 곤란한 자리에는 판
셋을, 많은 양을 빨리 훑어야 하면 판 하나를 쓴다.

### 글씨체마다 (벌마다 400줄)

![글씨체마다의 정확도](https://raw.githubusercontent.com/jysvai/ko-hand-ocr/main/bench-accuracy.svg)

합계 하나만 보면 **무너지는 글씨체가 가려진다.** 실제로 10%p 가 벌어진다.

| 글씨체 | 판 하나 (v62) | 판 셋 |
|---|---|---|
| **동해독도 (EastSeaDokdo)** | **88.5%** | **90.3%** |
| 기랑해랑 (KirangHaerang) | 93.3% | 93.8% |
| 하이멜로디 (HiMelody) | 94.6% | 95.6% |
| 나눔펜스크립트 (NanumPenScript) | 95.2% | 95.5% |
| 감자꽃 (GamjaFlower) | 97.8% | 97.8% |
| 싱글데이 (SingleDay) | 98.6% | 99.1% |

넘어야 하는 것은 평균이 아니라 **가장 낮은 벌**이다. 여섯 벌이 모두 90% 를
넘긴 뒤(2026-09-18) 목표를 95% 로 올렸다. 지금은 넷이 넘고 동해독도와
기랑해랑이 남았다. 이 두 벌은 획이 뭉개지고 생략되는 손씨다.

여섯 벌 다 **학습에 한 번도 안 쓴 글꼴**이고, 모두 SIL Open Font License 다.

```bash
python tools/holdout.py <판폴더> --per-font --sample sample.png
```

### 시험지가 실제로 어떻게 생겼나

![안 배운 글씨체 시험지](https://raw.githubusercontent.com/jysvai/ko-hand-ocr/main/holdout-sample.png)

글씨체마다 세 줄씩, 정답과 모델이 읽은 것과 닮음을 같이 적었다. 오른쪽의 옅은
띠는 64×640 틀에 맞추느라 남은 자리다 — 모델이 실제로 보는 그림 그대로다.

**여기 있는 짧은 서식 줄은 여섯 벌이 다 맞힌다.** 2026-09-02 에 같은 그림을
뽑았을 때는 동해독도의 '안전사무국' 이 틀렸는데 지금은 맞는다. 글씨체 사이가
벌어지는 자리는 이런 줄이 아니라 **긴 문장과 언어 지식이 안 통하는 줄**이다 —
시험지의 3분의 1은 뜻이 없는 음절을 이어 붙인 줄이라(획만 보고 읽는 힘을
기르려고 일부러 넣는다) 글자 하나만 어긋나도 되돌릴 여지가 없다.

생김새로 보면 **싱글데이**는 글자가 서로 떨어져 있고 획이 온전해서 인쇄체에
가깝고, **동해독도**와 **기랑해랑**은 획이 뭉개지고 생략된다. 아래 표의 차이가
그 차이다.

이 그림은 **글꼴 파일이 아니라 그림**이다. 글꼴로 글자를 그리는 것은 OFL 이
허용한다. 재배포하지 않는 것은 `.ttf` 파일 쪽이다
([PROVENANCE.md](https://github.com/jysvai/ko-hand-ocr/blob/main/PROVENANCE.md)).

## 속도와 사양 (실측)

GPU 가 필요 없다. 자모를 하나씩 차례로 뽑는 것이 병목이라 코어를 늘려도
별로 안 빨라지고, 반대로 **약한 PC 에서도 느려지지 않는다.**

CPU 로만, 사진 11장(칸 35개)을 재서 가운데값을 쓴다. 시간을 **자르기와 읽기로
나눠** 적는다 — 판을 줄여도 자르기는 안 줄고, 사진 한 장에 서너 줄뿐이면
자르기가 절반을 넘는다.

| | 자르기 | 읽기 | 사진 한 장(3.2줄) | 줄당 | 30줄 서류 한 쪽 |
|---|---|---|---|---|---|
| 판 하나, 빔 5 | 0.46초 | 0.53초 | 0.99초 | 0.17초 | 5.5초 |
| 판 하나, 그리디 | 0.46초 | 0.26초 | 0.71초 | 0.08초 | 2.9초 |
| 판 셋, 빔 5 | 0.47초 | 4.45초 | 4.92초 | 1.40초 | 42.4초 |

메모리는 판 하나 약 905MB, 판 셋 약 1.18GB. 2026-09-20 에 다시 쟀다.

**오른쪽 칸을 그냥 곱해서 얻은 것이 아니다.** 우리 시험 사진은 한 장에 서너
줄인데 남들이 말하는 「한 쪽」은 서른 줄짜리 서류다. 잰 쪽당 초를 그대로
들이대면 우리 쪽이 열 배쯤 유리한 숫자가 나온다. 그래서 묶음을 키워 가며
**줄당 초가 얼마나 내려가는지**를 재고 그 값으로 환산한다
(`python tools/bench.py --throughput`).

`python tools/bench.py --all --device cpu` 로 낸 값이다. 그 자는 앱이 지나는
길을 그대로 지난다 — 다른 길로 잰 속도는 쓰는 사람의 속도가 아니다.

## 돌아가는 곳

**Windows 에서 만들고 시험했다.** Windows 11 + Python 3.13/3.14 에서 학습과
판독을 모두 돌렸다.

| | |
|---|---|
| Windows | 만든 자리. 학습·판독 모두 확인 |
| macOS | **시험 중.** 판독은 순수 PyTorch + PIL 이라 돌 것으로 보지만 아직 확인 전 |
| Linux | 아직 안 해 봤다 |

`tools/train.ps1` 은 PowerShell 이라 Windows 전용이다. 다른 곳에서는
`python -m kohandocr.train` 을 직접 부르면 된다 — 그 대본이 하는 일은
앞 학습이 GPU 를 놓을 때까지 기다렸다가 띄우고 첫 걸음을 지켜보는 것뿐이다.

## 학습

데이터를 굽지 않는다. 글월을 만들고 손글씨 글꼴로 그려서 **그때그때** 먹인다.
그래서 디스크에 학습 데이터가 남지 않고, 분포를 바꾸면 다음 걸음부터 바로 반영된다.

```bash
python tools/fetch_fonts.py                       # OFL 손글씨 글꼴을 받는다
python -m kohandocr.train --out runs/v1 --layers 6 \
       --steps 20000 --batch 40 --workers 5 --letters 128
```

글꼴 자리는 이 차례로 찾는다. **경로를 코드에 박지 않는다.**

1. `--fonts` 로 준 값
2. 환경 변수 `KOHAND_FONTS`
3. `~/.cache/ko-hand-ocr/fonts`

`--layers` 를 안 주면 4층으로 만든다. 내놓는 판은 6층이다 — 4층은 조리법을
열세 바퀴 바꿔도 글씨체 평균 92.8~93.4% 에서 안 움직였고, 6층이 그 띠를 처음
넘었다. 층을 늘려서 치르는 CPU 속도는 25% 쯤이다(4층과 6층을 같은 자로 잰 값)
— 인코더와 입력 크기는 건드리지 않았다.

`fetch_fonts.py` 가 받는 것은 손글씨 글꼴 482벌이다. 그 가운데 **452벌로만
학습하고**, 여섯 벌은 위의 시험에, 스물네 벌은 「두루 읽나」에 쓴다. 시험용과
같은 디자인이 학습에 섞이면 숫자가 조용히 오르므로, 이름이 아니라 **그림으로**
견주어 닮음 0.7 이상이면 비켜 놓는다.

글꼴은 이 저장소에 들어 있지 않고 **재배포하지 않는다.** 나눔손글씨 109벌은
[clova.ai/handwriting](https://clova.ai/handwriting) 에서 받는다. 자세한 것은
[PROVENANCE.md](https://github.com/jysvai/ko-hand-ocr/blob/main/PROVENANCE.md).

합성이 실제 손글씨와 얼마나 닮았는지는 `kohandocr/measured.json` 에 적힌
실측 분포(잉크량, 밀도, 가로세로, 여백 등 아홉 가지)로 견준다.

```bash
python tools/match.py        # 과녁과 지금 합성을 나란히 본다
```

**오래 돌린다고 좋아지지 않는다.** 합성 분포를 바꾼 뒤에는 짧게 돌고 중간 판을
남겨서 골라야 한다(실측: 15,000걸음이 꼭짓점이고 30,000걸음은 오히려 내려갔다).

```bash
python tools/pick.py runs/v1-15000 runs/v1-30000    # 남긴 판들을 재서 고른다
```
